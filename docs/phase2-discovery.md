# Phase 2 — Deterministic verified component discovery

**Scope:** `apps/mcp-server` only. No changes to certified registry source,
manifests, evidence, or previous RES-002 benchmark data.

## What changed

`search_verified_components` now supports explainable task-intent ranking and
optional declared-runtime compatibility checks, without invoking Muse or any
other inference provider. It still calls the existing `selectTrustedComponents`
first, so `verification.status="verified"` and current certificate evidence
validation remain mandatory.

Example MCP input:

```json
{
  "query": "concurrent bookings with retries API",
  "nodeVersion": "24.15.0",
  "installedDependencies": { "zod": "4.6.7" },
  "limit": 5
}
```

Optional fields:
- `query`: natural language (max 500 chars); curated booking, cancellation,
  schema, concurrency, idempotency aliases plus conservative token coverage.
- `capabilities`: exact manifest capability names, all must match.
- `stack`: exact declared stack label (e.g. `node24+sqlite`).
- `nodeVersion`: exact target Node version (e.g. `v24.15.0`); manifest's
  declared minimum `>=major[.minor[.patch]]` is checked. Unknown ranges
  are conservatively considered incompatible when filtering is requested.
- `installedDependencies`: target dependency name/version map. Every
  package required by the component must match its exact pinned version;
  components with no external dependency requirements remain eligible.
- `limit`: max results; defaults to 10, maximum 25.

For a meaningful query, each hit includes an optional `match` object:

```json
{
  "score": 48,
  "matchedTerms": ["booking", "idempotency"],
  "signals": ["id:booking", "capability:idempotency"]
}
```

The numbers above merely illustrate the **shape**, not measured scores.
The actual score and explanation are computed from the registry metadata,
never generated by an LLM. No source text is included in search output.

Without a query, alphabetical `id@version` inventory order is retained.
With a query, ID matches outrank capability matches; invariant-only mentions
carry less weight. Ranking ties resolve lexicographically for determinism.
Unknown or unrelated task descriptions return no results rather than
silently recommending arbitrary components.

## Trust and compatibility boundaries

- Results are drawn exclusively from the registry's **currently trusted**
  selection; a stale or unverified manifest cannot be promoted by a match.
- `totalTrusted` is the complete certified catalog count, not the number
  of compatible or matching results.
- Empty results can mean **no task match** or **no declared runtime match**.
- Compatibility checks concern **declared metadata only**: they do not prove
  that the target application builds, resolves all transitive npm packages,
  or passes functional tests. That is Phase 3's verification responsibility.
- Search and ranking do not copy files, alter target dependencies or create
  new certification evidence.
